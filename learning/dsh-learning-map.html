世界观：所有 agent 框架共享的内核

1–2 小时

目标：在碰任何源码之前，握住业界共识的心智模型——agent harness = 除模型之外的一切：组装上下文、执行工具、记账（会话状态）、管安全（权限）。DSH、Claude Code、Codex 的内核同构。

读什么

  • 本目录的 dsh-agent-loop.html，只读「00 · 内核」和第 1 遍——七行伪代码就是全部。
  • Anthropic《Building Effective Agents》：workflows vs agents 的分界、保持简单、透明展示规划、精心设计工具接口。
  • Claude Code 官方文档《How the agent loop works》扫读：turn 的定义（一次「模型输出 + 工具执行 + 结果回填」往返）、权限三件套、上下文累积与自动压缩。

检查点（能回答再过关）

  • 默写七行循环；说出循环何时终止（模型不再发工具调用）。
  • harness 四件事分别是什么？为什么说「LLM 是 agent 系统里最小的部分」？
  • Claude Code 的 PreToolUse/PostToolUse hooks、只读工具并发执行，分别对应 DSH 的什么？（答案在关 5、关 6 揭晓，先带着问题走。）
深水区 · 用到再看
  • 论文《Dive into Claude Code》（arxiv 2604.14228）：对 Claude Code 设计空间的学术拆解。
  • 《How Codex is built》（Pragmatic Engineer）：Codex 把 harness 做成一个 Rust 共享库、CLI/IDE/Web 四端复用——和 DSH 的「一套包、多个 profile」是同一思路。
关 1

跑起来：亲手跑一次任务，找到它的账本

半天

目标：跑通 Web UI 和 headless 两条路径，亲眼看到一次运行在磁盘上留下的会话日志，并在 Trajectory 页认出事件流。

动手

# 前置：Node ^22.19 或 ≥24；DEEPSEEK_API_KEY 写进仓库根 .env（跑真模型需要）
pnpm install
pnpm run build          # tsc → tsdown → vite，首次必须完整构建
pnpm dsh web            # http://127.0.0.1:3080，界面里配模型、选工作区、跑一个小任务
# 或者命令行一把梭：
pnpm dsh --profile headless "用一句话介绍这个仓库"
  • 跑完后看 ~/.dsh/sessions/：按规范化工作目录分文件夹，里面每个 session-<uuid>/session.jsonl.zstd 就是一次会话的完整账本（默认 zstd 压缩）。
  • 回到 Web UI 打开 Trajectory（轨迹）标签页：它把账本摊开成 User / Assistant / Tool 记录，粗线是 turn 边界，还有时序总览（TTFT vs 解码）。这是理解 loop 最好的可视化入口。

检查点

  • 会话文件的路径规律是什么？web 和 headless 是不是同一个引擎？（是——同一批包，不同 profile。）
  • Trajectory 里一次工具调用显示了哪些信息（输入、输出、耗时、token）？
本机备忘（你踩过的坑）：更新代码走 git sync-diy，别手动动分支；同步上游后先 pnpm run clean 再 build；npm registry 用 npmmirror。
深水区 · 用到再看
  • apps/cli/reference/README.md：全部 flag（--port / --trusted-host / --no-open / --patch / --dump-config）。
  • SSH 环境下只打印 URL 不自动开浏览器；刻意不支持 --host 0.0.0.0。
  • 文档双轨：产品向 docs/user/guide/index.md，贡献者向 docs/development.md（Setup tutorial 节）。

目标：掌握全课程最重要的实验回路。快照测试从真实 dsh CLI 起进程，只有模型是回放的——工具、沙箱、持久化全是真的。之后每一关的「动手」都靠它验证。

动手

pnpm run test:snapshot -t text-turn     # 只跑一个场景，几秒出结果，不需要 API key

  • replay 模式为什么不需要 key？（dsh-llm-replay 适配器把日志里的 assistant/chunk 重组成流。）

  • 录制与刷新：test:snapshot:record（要 key）/ test:snapshot:refresh（不要）。

关 4

组装观：你跑的 dsh 是怎么拼出来的

半天–1 天

目标：看懂 profile → bundle → patch 的五层叠加，从此对「这个部署里有什么」有掌控感。

读什么

  • docs/architecture.md 全文（143 行，中枢地图）：重点是 profile/bundle 节、事件三域、结尾的「新行为该挂哪」映射表——以后做任何改动都会反复查这张表。
  • packages/bundle/base/cordis.patch.yml：86 个插件的真实主体，按功能分组扫一遍（LLM / 核心 / 持久化 / 沙箱审批 / 工具 / 子代理 / 上下文管理 / 命令）。再看 headless/cordis.patch.yml（30 行）体会「headless = base + 5 行差量」。
  • profile 不在仓库里，在 ~/.dsh/profiles/<name>/：空根 cordis.yml（别改）+ cordis.patch.yml（你的层）。五个模板：web / headless / sdk / sdk-minimal / acp。

动手

  • 编辑 ~/.dsh/profiles/web/cordis.patch.yml，把某个工具（比如 tool-todo）disable，重启 pnpm dsh web，观察模型工具表少了 todo_write；再改回来。
  • 对比 --dump-config 与 --dump-default-config 的差异，找到你自己 patch 层的痕迹。

检查点

  • 背出五层叠加顺序：profile 空根 ← bundles（按序）← profile 用户层 ← home 层 ← --patch。
  • web 与 headless 的差集是什么？（host HTTP 层 + 整排 client-ui-*；headless 无任何 UI，审批 fail-closed。）
深水区 · 用到再看
  • 启动链源码：apps/cli/src/bin.ts → args.ts → profile-boot.ts → packages/boot/app-boot；launcher 只解析自己的 flag，其余原样透传给 app。
  • settings.yaml（热重载的用户设置）与 cordis.patch.yml（组合层）的分工；credentials 按名引用密钥。

关 6

能力座与安全：吃透一个 seam，推得动二十个

2 天

目标：掌握全仓复用最多的形状——capability seam 三角色（Service Definition / Provider / Consumer）。fs、shell、web、lsp、terminal、skill、subagent、compaction 全是同一形状。

读什么

  • docs/glossary.md（45 行）：钉死 seam / scope / turn-step-round 术语，不读会一路误用。
  • 以 packages/fs/ 为模板走三角：fs（Definition，契约）→ fs-local / fs-sandbox（Provider，后端）→ tool-fs（Consumer，模型工具），外加 fs-observation-policy（「策略也是独立包」的范例）。
  • 对照 packages/shell/ 验证同构：shell → bash-local → tool-bash；它的 request/spec 拆分是「显式 resolve、拒绝隐藏默认值」的仓库模板。
  • 安全链：sandbox-policy 三档（read-only / workspace-write / danger-full-access）、user-approval（headless 无 answerer 时 fail-closed 成 unavailable）、permission-presets、guard/ 两个小守卫。

动手

  • 从 tool-fs 的 execute 往下追一次 read 的调用栈到 fs-local，画出三角色依赖箭头。
  • 把 profile 的 sandbox 模式改成 read-only，跑一个要写文件的任务，观察拒绝如何以工具结果的形式回给模型（而不是崩溃）。
  • 跑 snapshots/acp/ 的 escalation 场景，看审批回路怎么走。

检查点

  • 三角色各在哪个包？依赖方向是什么？「扩展插件只依赖 Definition、绝不依赖 Provider」为什么是铁律？
  • headless 下审批为什么确定性拒绝？DSH_PERMISSION_MODE=danger-full-access 改变了什么？
深水区 · 用到再看
  • subprocess/：所有子进程的唯一入口（可执行查找、有界输出、整树终止）。
  • 沙箱三平台后端：Linux bwrap/Landlock（native/landlock-run）、macOS Seatbelt、Windows 受限令牌。
  • docs/subsystems/approval.md、sandbox.md、shell.md、filesystem.md。

读一个包的固定套路

① 包 README（含 Model Experience 节：它对模型/token/KV cache 的影响）→ ② 对应 docs/subsystems/ 页（类型与语义的权威定义）→ ③ src/types.ts（纯类型）→ ④ src/index.ts → ⑤ tests/（行为即文档）。
